Integraties die nog niet op [OAuth 2.0](/knowledgebase/nl/integrations/api-authentication) werken, authenticeren met de legacy-aanmelding. U meldt zich één keer aan met het e-mailadres en wachtwoord van een API-gebruiker, ontvangt een token, en stuurt daarna het token en het e-mailadres bij elk verzoek mee.

De endpoints, payloads en responses zijn hetzelfde als in de rest van deze referentie. Alleen de basis-URL en de `Authorization`-header zijn anders.

## Uw API-URL

Elke Clarus-omgeving heeft een eigen API-URL, opgebouwd uit uw subdomein:

```text
https://{subdomain}.api.clarus.ws
```

Is uw subdomein bijvoorbeeld `acme`, dan is uw API-URL `https://acme.api.clarus.ws`. Weet u uw subdomein niet zeker, neem dan contact op met Clarus support.

| Pad | Gebruik |
|---|---|
| `/users/sign_in` | Aanmelden om een token te krijgen |
| `/api/...` | REST-endpoints, bijv. `https://acme.api.clarus.ws/api/products` |
| `/graphql` | GraphQL-queries |

<Info>Heeft u een sandbox-omgeving, dan heeft die een eigen subdomein. Vul dat subdomein in de URL in om uw integratie naar de sandbox te laten wijzen.</Info>

Werkt u vanuit de **Operations**-referentie, vervang dan `https://clarus-api.com` door uw API-URL. De `X-Clarus-Subdomain`-header is niet nodig, omdat de URL uw omgeving al aangeeft.

## Aanmelden en verzoeken authenticeren

<Steps>
  <Step title="Aanmelden">
    Stuur het e-mailadres en wachtwoord van de API-gebruiker naar `/users/sign_in`:

    ```bash
    curl -X POST https://acme.api.clarus.ws/users/sign_in \
      -H "Content-Type: application/json" \
      -d '{
        "user": {
          "email": "api.user@example.com",
          "password": "your-password"
        }
      }'
    ```

    Een geslaagde aanmelding geeft `201 Created` terug met het token:

    ```json
    {
      "user_id": 42,
      "token": "23Ya-sdFas7E3sMH9xgt",
      "email": "api.user@example.com",
      "auth_status": "legacy"
    }
    ```

    Onjuiste inloggegevens geven `401 Unauthorized` terug.
  </Step>
  <Step title="Stuur het token bij elk verzoek mee">
    Voeg een `Authorization`-header toe met zowel het `token` als het `email` uit de aanmeldresponse:

    ```text
    Authorization: Token token="23Ya-sdFas7E3sMH9xgt", email="api.user@example.com"
    ```

    Bijvoorbeeld:

    ```bash
    curl https://acme.api.clarus.ws/graphql \
      -H 'Authorization: Token token="23Ya-sdFas7E3sMH9xgt", email="api.user@example.com"' \
      -H "Content-Type: application/json" \
      -d '{"query": "{ accounts { all { edges { node { id code name } } } } }"}'
    ```

    Het voorvoegsel `Bearer` wordt ook geaccepteerd, zolang het e-mailadres erbij staat: `Authorization: Bearer token="…", email="…"`.
  </Step>
  <Step title="Hergebruik het token">
    Bewaar het token en gebruik het voor elke aanroep. Meld u alleen opnieuw aan wanneer een verzoek `401 Unauthorized` teruggeeft.
  </Step>
</Steps>

## Elke aanmelding vervangt het token

Een gebruiker heeft maar één legacy-token tegelijk. Elke aanmelding geeft een nieuw token uit en maakt het vorige ongeldig, en een aanmelding in de WMS-front-end met hetzelfde account kan hetzelfde doen. Afmelden via `/users/sign_out` maakt het token ook ongeldig.

Dit betekent:

- **Gebruik een aparte API-gebruiker.** Meldt iemand zich in de front-end aan met het account van de integratie, dan werkt het token van de integratie niet meer. Zie [Gebruik een apart gebruikersaccount](/knowledgebase/nl/integrations/api-authentication#gebruik-een-apart-gebruikersaccount).
- **Meld u niet bij elk verzoek aan.** Aanmelden bij elke aanroep sluit andere processen af die hetzelfde account gebruiken. Hergebruik het opgeslagen token en meld u pas opnieuw aan na een `401`.
- **Geef elk systeem een eigen gebruiker.** Twee integraties die één account delen, maken elkaars tokens steeds ongeldig.

## Behandel inloggegevens als geheimen

Het wachtwoord en het token geven allebei toegang tot uw magazijngegevens. Bewaar ze in een secrets manager of omgevingsvariabelen, nooit in versiebeheer en nooit in gedeelde documenten.
